# Timed workflow activation

A saved draft, immutable publication, timed activation and accepted run have separate lifecycles. The schedule APIs are `workflows.schedules.preview`, `.read`, `.enable` and `.disable`. Preview/read require Read scope; enable/disable require Write. The verified connection supplies the owner. A schedule pins an explicitly selected publication and input; publishing another release never retargets it. Enable checks the publication's actual graph and preparation capabilities without executing handlers or inference. Readiness is rechecked before every automatic admission.

The elapsed timing forms are one-time UTC instants and fixed elapsed intervals anchored to a start instant, with an optional inclusive end. Intervals are one minute through one year. Preview shows the next five actual instants. A day means 24 elapsed hours, so its local clock time can move at daylight-saving changes. Calendar schedules additionally support a selected local time, ISO weekdays (Monday 1 through Sunday 7), a named IANA timezone, inclusive start/end local dates and up to 366 unique excluded dates. UTC offsets are not timezone names. Each selected date contributes at most one occurrence. The explicit missing-time policy either skips that date or uses the first valid instant after the clock gap on the same date (02:30 becomes 03:00 for a one-hour spring gap). If the entire local date is missing, it is skipped. Repeated times choose the first occurrence, second occurrence, or skip the date. Preview returns UTC instants; the page renders them in the chosen timezone with their actual offsets. The portable Temporal implementation is shared by SDK and server; calendar arithmetic does not introduce another execution engine.

Calendar recovery scans at most 64 local dates per dispatch pass. Its original outage horizon, count and bounded pending candidates are persisted across worker restarts and competing dispatchers. No run is admitted from an incomplete scan. Catch-up caps apply to the whole captured window, not separately to each pass. Dates beyond an inclusive end are never scanned. Invalid stored timing parks the schedule as blocked, with the failure message available for review. Completion-relative intervals and connected-event triggers remain unfinished.

An activation starts at the first occurrence strictly after enable commits its reviewed timestamp. Time spent disabled is not backfilled on re-enable. Skip policy discards occurrences older than the explicit lateness grace, latest policy coalesces missed occurrences into the latest one, and catch-up replays the oldest occurrences up to the configured limit (at most twenty), discarding the rest. The recovery cursor advances past the whole evaluated window, so restarting between dispatches does not reset the cap. Overlap counts all queued, running and waiting scheduled runs for this owner/workflow, including prior activation revisions. Occurrences at the configured limit are skipped, rather than growing a queue without a bound. Skipped counts and the last outcome are visible; accepted results/events stay in the existing run journal.

MongoDB owns the registration and bounded pending batch in `workflow_schedules`; `workflow_schedule_commands` contains idempotent enable/disable receipts. A due/status index provides bounded discovery (sixteen registrations per pass). No collection of all users' schedules is loaded into process memory, and no SQLite lock or browser timer is involved. Command revisions fence competing configuration changes. Receipts replay without rewinding current state, including old enable retries after a later disable. There is currently one timed registration per workflow; multiple independent trigger registrations are still open work.

Scheduled admission records immutable schedule revision and occurrence time on the existing published run snapshot/summary. Its deterministic owner-scoped run identity, removal from the bounded pending batch, publication/deletion fence, and run acceptance commit in one transaction. Process death or a failed transaction leaves the occurrence recoverable. Competing workers cannot accept it twice. Disable/reconfiguration racing preparation invalidates the old occurrence before acceptance. Disable discards unaccepted pending occurrences; already accepted runs remain inspectable and use their separate cancellation control. Deletion prevents further admission while retaining evidence.

The existing workflow queue starts a bounded schedule discovery loop alongside run discovery. `nexa serve`, channels and the standalone workflow worker use it whenever workflow workers are enabled. Gateway sessions do not own automation lifetime. Shutdown aborts dispatch waits and rejects late acceptance; preparation has a thirty-second observation deadline. A readiness failure parks the registration as blocked with an actionable message, instead of repeatedly retrying the same failed connection. The owner can review setup and enable again. All accepted work uses the existing leases, durable waits, cancellation, execution handlers and billing evidence.

Deploy gateways, workers and the typed SDK together before enabling schedules against a shared database. Older readers do not understand the new optional schedule provenance. No migration, retention deletion, live schedule or service restart is performed by this change. Enable does not add financial reservations, run-only sharing, event subscriptions; those remain separate requirements.

Calendar timing adds a new wire union variant. Deploy gateways, workers and clients together before using it with a shared database. Existing fixed-interval and one-time records do not need rewriting.
